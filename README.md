# modelcheck

[![tests](https://github.com/zhilikj/modelcheck/actions/workflows/test.yml/badge.svg)](https://github.com/zhilikj/modelcheck/actions/workflows/test.yml)
[![PyPI](https://img.shields.io/pypi/v/llm-modelcheck.svg)](https://pypi.org/project/llm-modelcheck/)
[![Python 3.8+](https://img.shields.io/badge/python-3.8%2B-blue.svg)](https://github.com/zhilikj/modelcheck)
[![dependencies: none](https://img.shields.io/badge/dependencies-none-brightgreen.svg)](https://github.com/zhilikj/modelcheck)
[![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](https://github.com/zhilikj/modelcheck/blob/main/LICENSE)

检测一个大模型 API 端点有没有在**掺水**：换了模型、降级到便宜型号、或者把功能阉割掉。

零依赖，Python 3.8+。支持 OpenAI 兼容接口（覆盖绝大多数中转站、DeepSeek、Qwen、Kimi、GLM、Groq、OpenRouter），也支持 Anthropic 和 Gemini 的原生接口。

**CI 在四个环境上跑过：Python 3.8 / 3.10 / 3.12 + Windows 3.12，39 个测试全绿。**

```bash
pip install llm-modelcheck

modelcheck self-test          # 先自检，确认工具本身没毛病（44 项，不联网）
modelcheck run \
    --base-url https://api.example.com/v1 \
    --api-key sk-xxx \
    --model gpt-4o
```

> **包名是 `llm-modelcheck`，命令是 `modelcheck`。**
> `modelcheck` 这个包名在 PyPI 上已被一个俄语的同类工具占用，所以加了 `llm-` 前缀区分。
> 命令名保持短的，因为你要天天敲它。

**不想装也可以**，直接下单个文件跑（零依赖，不需要 pip）：

```bash
curl -O https://raw.githubusercontent.com/zhilikj/modelcheck/main/modelcheck.py
python modelcheck.py run --base-url ... --api-key ... --model gpt-4o
```

## 一次真实的判定

下面这个例子是一个**声称自己是 gpt-4o、实际走 cl100k_base**（gpt-4 / 3.5 那一代）的端点。
这是最常见的一种掺水：模型名不改，后端换个便宜的。

```
  [+] 用量稳定性        5 次一致（样本 126 token）
      固定开销（只发 'ping' 也要付的部分）：9 token

  [X] 分词器指纹        词表是 cl100k_base，但声称的是 o200k_base
      探针增量（参照列是「声称的那个词表」应有的值）：
        han_dup   实测   50   参照   50   偏差   0.0%
        han_rare  实测  300   参照  260   偏差  15.4%
        emoji     实测  180   参照  140   偏差  28.6%
        real_cn   实测   99   参照   69   偏差  43.5%
        mix       实测  110   参照   70   偏差  57.1%
      与参照的平均相对误差：
        cl100k_base     0.0% ← 最接近
        o200k_base     28.9%

  [+] 功能矩阵         7/7 全部通过
  [+] 能力基线         10/10 通过（100%）
  [+] 上下文窗口        至少接受 32000 字符
  [+] 错误码规范性       密钥无效返回 401

------------------------------------------------------------------------
  结论：高度疑似不一致
    [X] 分词器指纹与声称的模型不符
```

注意这里有个反直觉的地方：**功能全过、能力题满分，照样被抓出来了。**

因为它本来就是一个正常的 OpenAI 模型 —— 只是不是它声称的那一代。
所以「能力测试」这类办法查不出它，词表可以。

## 两次真实端点的验证结果

工具做出来之后在两个真实端点上跑过，一次验的是「能不能抓到问题」，一次验的是「参照表是不是对」。

### 第一次：Claude 端点（用来发现缺陷）

`claude-fable-5-2`，返回 Anthropic 原生的 `msg_01…` 消息 ID。这次跑出了三个真实缺陷，全部修掉：

| 缺陷 | 表现 | 原因 |
| --- | --- | --- |
| 推理模型吃掉 max_tokens | 能力题返回空、流式 0 字 | `max_tokens=30` 被 thinking 用光，正文一个字没出 |
| 拿 OpenAI 标准要求 Claude | `logprobs` / `seed` 被记成「缺失」 | Anthropic 原生接口本来就没有这两项 |
| 题库有歧义 | 一道题返回空 | 「3×3 的方格」可理解为 9 个格子（20 条路）或 9 个格点（6 条路） |

**★ 这次吻合率是 0.0%，但那个 0.0% 不算证据** —— Claude 的词表参照就是从这台端点测出来的，拿它再验同一台，必然吻合。**这是循环论证。**

### 第二次：gpt-6-astra（这次是真验证）

**参照表是本地 tiktoken 算的，和这个端点毫无关系。跑出来 0.0% 全中：**

```
探针          实测    o200k   cl100k   claude
han_dup        50       50      50      100
han_rare      260      260     300      260
emoji         140      140     180      180
real_cn        69       69      99      102
mix            70       70     110      101

o200k_base            0.0%  ← 最接近
cl100k_base          20.4%
anthropic_claude     27.1%
```

**能力题 10/10，判定「未发现替换迹象」。**

**这同时证明了两件事：**

1. **本地算出来的 o200k 参照是对的** —— 它能和真实端点的 `usage` 完全对齐
2. **探针方法在真实环境下有效** —— 不是只在本地假端点上自嗨

**★ 这次跑又抓出两个缺陷：**

| 缺陷 | 表现 | 修法 |
| --- | --- | --- |
| `max_tokens=1` 被上游拒 | HTTP 400「max_tokens 不够」 | 按 1 → 8 → 32 → 128 逐级试探，成功值缓存 |
| 把模型的限制当成网关的问题 | `stop`、`tools` 报 400 被记成「功能缺失」 | 识别上游文案 `not supported` / `Unsupported parameter`，标成「不适用」 |

**「上游明确说这个模型不支持」和「网关没实现」是两件事。** 前者不是问题，后者才是。

### 第三次：glm-5.3-flash（验证「无参照时会不会瞎猜」）

**先不加参照跑了一次，结果符合预期：**

```
[-] 分词器指纹        模型 glm-5.3-flash 没有内置参照词表，跳过
结论：部分项目无法判定
```

**这就是「只做证伪」该有的样子 —— 测不出来就说测不出来，不给一个看起来有用的假分数。**

然后把这个端点的实测指纹加成第四套参照（`glm_zhipu`）：

```
探针          实测    glm    o200k   cl100k  claude
han_dup        50     50      50      50     100
han_rare      240    240     260     300     260
emoji         100    100     140     180     180
real_cn        54     54      69      99     102
mix           110    110      70     110     101

glm_zhipu             0.0%  ← 最接近
cl100k_base          22.0%
o200k_base           23.0%
anthropic_claude     31.6%
```

**再次抓出一个缺陷：** 推理型模型的 `seed` 不可复现，原来会记成「同 seed 两次输出不同」——
**但思考过程本身是随机的，seed 管不住它，这不是网关的问题。** 已改成检测到推理行为时标「不适用」。

**★★ 同样要说明：这次 0.0% 也是循环论证 —— 参照来自这台端点。**

### 第四次：kimi-k3.1-pro（最严重的一类缺陷）

**这个模型只接受 `temperature=1` 或不传，传 0 直接 400。**

| temperature | 不传 | 0 | 0.01 | 0.2 | 1 |
| --- | --- | --- | --- | --- | --- |
| 结果 | 200 | **400** | **400** | **400** | 200 |

**而工具默认全程用 `temperature=0` 保证确定性 —— 在这个模型上所有探针都会 400，整个工具直接废掉。**

**这一类缺陷比前面几个都严重：不是某一项测不出，是全部测不出。**

修法：先在 400 时换 1，再不行就不带这个参数，成功一次就锁定。

**★ 顺带纠正一句容易搞混的话**：`temperature` 不影响指纹。`prompt_tokens` 只取决于输入怎么分词，和采样温度无关。它影响的是**能力题** —— 温度不为零，同一道题两次可能答得不一样。

**这次的指纹（供参考，没有内置）：**

```
han_dup 50（0.50/字） han_rare 240（2.00/字） emoji 180（3.00/个） real_cn 51（0.52/字） mix 70
```

## 自己建基线：`--profile`

**这是这个工具最实用的功能，也是解决「模型太多、参照不够」的正解。**

内置参照只有四套。但你有官方 API 的 key 时，可以自己给任意模型建一份基线，然后拿它去验第三方渠道：

```bash
# 第一步：在官方接口上建基线（或你信得过的那条渠道）
modelcheck fingerprint \
    --base-url https://api.moonshot.cn/v1 \
    --api-key sk-official-xxx \
    --model kimi-k2 \
    --out kimi-official.json

# 第二步：拿这份基线去验中转站
modelcheck run \
    --base-url https://some-relay.example.com/v1 \
    --api-key sk-relay-yyy \
    --model kimi-k2 \
    --profile kimi-official.json
```

**当 `--profile` 里的模型名和 `--model` 完全一致时，这份基线会成为「期望参照」** —— 也就是用官方指纹去核对第三方给的是不是同一个模型。这一项吻合，说明两边的分词器是同一套。

**★ 几个必须知道的边界：**

| 情况 | 行为 |
| --- | --- |
| 基线模型名 ≠ 当前模型 | 基线仍参与比较，但**不会**成为期望参照（防止拿 A 的基线判 B） |
| 拿 pro 的基线验 flash | 会得出「不匹配」，但两者可能只是同族不同型号 —— **别据此定罪** |
| 基线自检没通过 | 文件照写，但标记 `selftest_ok: false`，说明这份基线不可靠 |
| 端点只接受特定 temperature | 基线里会记下，指纹本身不受影响 |

**基线文件是普通 JSON，可以直接放进 Git 仓库共享。** 一个团队里只要有一个人用官方 key 建过基线，其他人验中转站就不用再建。

## 六个探针，各自能证明什么

| 探针 | 测什么 | 能证明什么 | **不能**证明什么 |
| --- | --- | --- | --- |
| **分词器指纹** | 固定文本在不同词表下的 token 数 | 换模型**必然**换词表，这一项最硬 | 同词表下的不同型号（4o / 4o-mini / 4.1 / 5）区分不了 |
| **用量稳定性** | 同一输入重复 5 次、分项与总量是否自洽 | 计费链路稳不稳 | 账算得**准不准** |
| **功能矩阵** | logprobs / JSON 模式 / 工具调用 / seed / stop / max_tokens / 流式 | 网关有没有实现这些能力 | 模型真假（可能是真模型但网关太简陋） |
| **能力基线** | 10 道答案唯一、可机器校验的题 | 后端**水平**够不够 | 后端**身份**。真模型也会失手 |
| **上下文窗口** | 逐步加长输入，找第一次失败的位置 | 标称值和实际差多少 | 进去了还记不记得（那是另一个测试） |
| **错误码** | 401 / 404 / 429 是否规范 | 这个网关好不好接 | 跟模型真假完全无关 |

### 功能矩阵会按模型族调整标准

**拿 OpenAI 的标准去要求 Claude 会得出错误结论** —— Anthropic 的原生接口本来就没有 `logprobs` 和 `seed`，网关不返回它们是对的，不是「功能被阉割」。

所以这些项在 Claude 模型下会标成「不适用」，只记录、不计分：

```
  - logprobs      不适用：Anthropic 原生接口没有 logprobs，缺失属正常
  - seed 可复现      不适用：Anthropic 原生接口没有 seed 参数，不可复现属正常
  通过 5/5 项（另有 2 项不适用）
```

### 推理型模型会吃掉 max_tokens

Claude 的 thinking、o1/o3 的 reasoning 会先花掉一批 token 在推理上，再输出正文。`max_tokens` 给少了，正文会是空的 —— 这会被误读成「模型答不出来」。

工具会自动识别这种情况：正文为空但收到了 `reasoning_content`，就加大预算重试一次，并在报告里注明。

流式探针也单独统计推理块。**只收到推理内容、没有正文，说明模型在思考，不是「没流式」。**

### 为什么不用「问它你是谁」

最不靠谱的办法，但被用得最多。

同一个模型换几种问法能给你三四个答案。模型对自己的身份认知本来就模糊，系统提示词又能改它怎么答。你问出「我是 GPT-4」，可能是真的，也可能只是提示词里写了。

**这个工具不做这件事。**

### 为什么不用价格判断

批量采购价和零售价不是一回事。贵的不一定真，便宜的不一定假。用价格推模型，那是猜。

### 为什么不用单次延迟

噪声太大。同一天不同时段能差一倍，跟网络、排队、上下文长度都有关。除非测几百次看分布，单个数字说明不了什么。

## 分词器指纹是怎么做的

这是整个工具里唯一「硬」的判据，值得单独说。

**核心事实**：分词器（BPE 词表）是模型自带的，换模型**一定**会换词表。这是模型厂商训练时就定死的，网关改不了。

**做法**：发几段固定文本，用 `prompt_tokens` 的**增量**反推词表。

```
增量 = prompt_tokens("ok" + 探针文本) − prompt_tokens("ok")
```

用增量而不是绝对值，是为了抵消端点偷偷加的固定前缀（系统提示、角色模板这些常量都会被差分消掉）。

**五段探针的区分度**（tiktoken 0.14.0 实测，扣掉基线）：

| 探针 | 内容 | o200k_base | cl100k_base | 倍差 |
| --- | --- | --- | --- | --- |
| `mix` | `API 网关和 token 预算` × 10 | 70 | 110 | **1.57×** |
| `real_cn` | 真实中文技术段落 × 3 | 69 | 99 | **1.43×** |
| `emoji` | 🦙🐉🌏 × 20 | 140 | 180 | 1.29× |
| `han_rare` | 龘靐齉爩鱻麤 × 20 | 260 | 300 | 1.15× |
| `han_dup` | `测试` × 50 | 50 | **50** | 1.00× |

`mix` 和 `real_cn` 差 40%~57%，足够把两套词表分开。

### 那个 1.00× 的探针是干什么的

`han_dup` 在两套词表下**都**是 50。它不参与判别，它是**自检**：

如果实测出来不是 50，说明 `usage` 根本不是后端分词器的真实结果 —— 可能是中间层自己重算的。这时候整个指纹比对失效，工具会明确输出「**这条线索断了**」，而不是给一个看起来有用的假分数。

只靠这一条还不够。**「字符数 ÷ 2」这种粗糙重算恰好会给出 50**（`测试`×50 正好 100 个字符）。

所以还有第二重自检：`han_rare / han_dup` 的比值应该在 **5.2~6.0** 之间。真实的 BPE 词表会把罕见汉字拆成好几个 token，比值接近 6；按字符数拍脑袋的算法只有 1.2，差一个数量级。

两条都过，才继续比词表。

### 四套参照，分两个置信度

| 参照 | 覆盖 | 置信度 | 依据 |
| --- | --- | --- | --- |
| `o200k_base` | gpt-4o / 4.1 / 5 / **6**、o1 / o3 / o4 | **measured** | 本地 tiktoken 实测，任何人可复现 |
| `cl100k_base` | gpt-4 / 4-turbo / 3.5、text-embedding-3 | **measured** | 同上 |
| `anthropic_claude` | Claude 全系 | **observed** | 2026-11-26 通过真实网关实测 |
| `glm_zhipu` | 智谱 GLM 全系 | **observed** | 同上 |

**置信度直接决定「不匹配」这个结论有多硬：**

- 你声称的是 **measured** 参照覆盖的模型（OpenAI 系）→ 我们很清楚它该长什么样，**不匹配就是强证据，判 fail**
- 你声称的是 **observed** 参照覆盖的模型（Claude / GLM）→ 参照本身只有一处来源，**不匹配只能是弱信号，判 warn**

其它词表族（Gemini、Llama、Qwen、Mistral）没有参照，探针明确跳过：

```
[-] 分词器指纹        模型 gemini-2.5-pro 没有内置参照词表，跳过
    内置参照：anthropic_claude、cl100k_base、glm_zhipu、o200k_base
```

这时候工具会告诉你「部分项目无法判定」，而不是假装测过了。

### 四套词表的指纹对比

| 探针 | o200k | cl100k | Claude | GLM |
| --- | --- | --- | --- | --- |
| `han_dup`（`测试`×50） | 50 | 50 | **100** | 50 |
| `han_rare`（罕见汉字×20） | 260 | 300 | 260 | **240** |
| `emoji`（🦙🐉🌏×20） | 140 | 180 | 180 | **100** |
| `real_cn`（真实中文×3） | 69 | 99 | 102 | **54** |
| `mix`（中英混排×10） | 70 | 110 | 101 | 110 |

**翻成「每个字多少 token」更直观：**

| 词表 | 常用汉字 | 罕见汉字 | emoji |
| --- | --- | --- | --- |
| o200k_base | 0.50 | 2.17 | 2.33 |
| cl100k_base | 0.50 | 2.50 | 3.00 |
| Claude | 1.00 | 2.17 | 3.00 |
| **GLM** | **0.50** | **2.00** | **1.67** |

**GLM 对中文和 emoji 都比 OpenAI 省** —— 这符合它作为中文原生模型的定位，也说明这四套指纹确实互相可区分。

### Claude 那套参照是怎么来的，以及它的局限

2026-11-26 拿一个真实网关（返回 Anthropic 原生的 `msg_01…` 消息 ID 和 `input_tokens` 字段）实测，五个探针的增量是：

```
han_dup  100      han_rare  260      emoji  180      real_cn  102      mix  101
```

**为什么能判断它透传的是真词表、不是自己算的：**

| 文本 | 增量 | 每单位 |
| --- | --- | --- |
| `测试`×50（100 个常用汉字） | 100 | **1.00 / 字** |
| 罕见汉字×20（120 字） | 260 | **2.17 / 字** |
| emoji×20（60 个） | 180 | **3.00 / 个** |

常用字 1.0、罕见字 2.17、emoji 3.0 —— **这个梯度只有真 BPE 词表能产生。按字符数拍脑袋的算法对所有字符一视同仁，单价会是一条平线。**

**但必须说清楚两条局限：**

1. **只有一处来源，没和 Anthropic 官方交叉验证过。** 万一那个网关本身有问题，这套参照就是错的。所以它只敢判 warn，不敢判 fail。
2. **从同一台端点测出来的参照，拿去验同一台端点，结果是必然吻合的。** 那是循环论证，不能当作「这台端点验过了」的证据。它的真实用途是验**别的** Claude 端点。

如果你有 Anthropic 官方 key，欢迎把实测值提 issue 替换掉这套 observed 参照。

## 它测不出来的东西

说清楚这个，比多列三个优点有用。

| 测不出来 | 为什么 |
| --- | --- |
| **跑路风险** | 技术上无法验证。预充值永远从小额开始，这条没有替代方案 |
| **数据留存** | 请求有没有被记录、留多久、会不会出境，只能靠书面确认 |
| **同词表下的型号替换** | 4o 换成 4o-mini，词表一样，指纹看不出来。要靠能力题和纵向对比 |
| **混合路由** | 简单问题走便宜模型、难问题走贵的。单次测试看不出来，必须长期采样 |
| **有效上下文** | 这里只测「输入进得去」，没做「针在草堆里」那种记忆测试 |
| **并发掺水** | 承诺的并发达不到。这个要看压测，不是本工具的范围 |

还有一条最重要的：

> **这个工具只做证伪，不做证真。**
> 「未发现替换迹象」不等于「确认真模型」，只是「用这些办法没抓到」。

---

## 单次结果没有意义，趋势才有意义

模型被换掉的那天，曲线会跳。所以工具带基线功能：

```bash
# 第一次，存基线
modelcheck run --base-url ... --model gpt-4o --save-baseline base.json

# 过几天再跑，和基线比
modelcheck run --base-url ... --model gpt-4o --compare-baseline base.json
```

输出会列出每个探针从什么变成了什么，并标出变化项。

**建议放进定时任务，每天或每周跑一次。** 单次「通过」只能说明当时没事。

## 常用选项

```
--api openai|anthropic|gemini   接口类型，默认 openai
--only usage,tokenizer          只跑指定探针
--skip context                  跳过指定探针
--json report.json              结构化结果
--markdown report.md            可直接贴进工单的报告
--deep-context                  上下文探针探到 128000 字符（默认 32000 就停，省钱）
--insecure                      跳过 TLS 证书校验（自签名证书用）
--quiet                         只输出结论
```

**退出码**：`0` = 没发现强证据（可能有个别 warning），`1` = 高度疑似不一致，`3` = 全部探针执行失败（什么都没测出来）。可以直接用在 CI 里。

**关于成本**：一次完整跑大概发 35~40 个请求，其中大部分 `max_tokens=1`，输出成本可以忽略。计入成本的主要是上下文探针那几发长输入 —— 默认上限 32000 字符，按 gpt-4o 的输入价算不到一美分。加 `--deep-context` 会明显变贵。

## 为什么做这个

最近一两个月，好几家媒体在报这个行业的乱象：计费黑箱、封号跑路、模型降智、倒卖用户数据。搜「token 中转站」，十篇文章里八篇是在讲风险。

这些报道讲的大多是行为和后果。但开发者真正需要的是一句话的答案：**我手上这个端点，现在到底是不是它说的那个。**

这个问题技术上是有办法回答一部分的。所以把内部一直在用的检测逻辑整理成了这个工具。

**它不推销任何东西** —— 不联网、不需要注册、不指向任何服务。你拿它去测任何一家，包括我们自己，都一样跑。

## 开发

```bash
python -m unittest discover -s tests -v     # 39 个测试，全部跑在本地假端点上，不联网
python modelcheck.py self-test              # 不联网的自检，验证参照数据和判定规则
```

测试里有一个假端点（`tests/mock_endpoint.py`），能精确模拟四种行为：

- **real** —— 诚实端点：o200k 词表、功能齐全、能力题全对
- **downgrade** —— 降级：声称 gpt-4o，实际 cl100k
- **fake** —— 套壳：词表对不上、功能缺失、能力题答错
- **recomputed** —— `usage` 被端点自己重算

测试验证的是：**同一条探针，对这四种端点给出的结论方向是否正确**。尤其是第三种情况 —— 一个不成熟的工具会在那里给出一个假结论。
